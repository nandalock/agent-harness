本稿依据当前仓库代码、设计文档和公开资料编写；项目起止时间需按实际经历填写。简历写法于 2026-10-11 重新检索并核对。

## 项目名称的公开参考

推荐名称：**智能体运行平台（Agent Harness）**。这是结合官方术语和本项目实现范围整理的中文简历名称。

- [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) 官方直接将项目定位为开源 agent harness。
- [LangChain Deep Agents](https://github.com/langchain-ai/deepagents) 官方将其定位为 agent harness，提供文件系统、上下文管理、工具和人工介入等能力。
- [Microsoft Agent Harness](https://learn.microsoft.com/en-us/agent-framework/concepts/harness) 将 Harness 定义为驱动模型及工具调用、管理对话状态与上下文、应用审批策略的运行支撑层。
- [Letta](https://docs.letta.com/) 使用构建有状态智能体的平台这一定位。

本项目具有执行循环、工具调度、会话持久化、权限审批和管理界面，因此采用“运行平台”描述交付形态，并用“Agent Harness”说明技术核心。

## 可直接放入简历的版本

**智能体运行平台（Agent Harness）｜个人项目｜独立开发**

**项目链接：** [github.com/nandalock/agent-harness](https://github.com/nandalock/agent-harness)

**技术栈：** Python、FastAPI、asyncio、PostgreSQL、MCP、Docker、Next.js、TypeScript。

**项目描述：** 面向知识问答与多步工具任务，开发可配置的智能体运行平台，提供可视化工作流、会话工作区和执行追踪，支持多轮对话及运行中人工干预。

- **工具调度优化：** 针对多工具串行等待，基于 asyncio 实现默认 4 路滚动并发、独占屏障与结果按序提交；在 12 次 × 100ms 本地模拟 I/O 基准中，各测 5 轮，批次中位耗时由串行的 1.33s 降至 0.35s，减少约 74%。
- **运行稳定性：** 针对异常重试与重复工具调用导致的失控，为 LLM–Tool 循环设置步数、调用次数与总时长预算，结合有限重试、重复调用检测和取消传播约束异常执行，支持取消时保留已生成正文。
- **会话一致性与恢复：** 针对历史、模型上下文与轨迹分散维护的问题，以 Event Log 统一派生状态，通过 PostgreSQL 事件写入去重和中断修复支持重启后续聊；12 项恢复测试全部通过，覆盖工具结果缺失、轮次闭合及重复修复。
- **执行权限控制：** 设计 3 种文件权限模式，受限 Bash / Python 调用通过 Docker 控制工作区访问与资源占用；超出当前权限的执行须人工审批，授权仅作用于单次调用，控制工具执行的文件访问边界。
- **运行中交互控制：** 优化长任务的指令调整流程，通过 2 条输入队列区分当前轮修正与下一轮追加，在步骤边界注入上下文；使用 SSE 回执同步投递状态，支持运行中调整任务方向，并防止同一进程内重复启动会话任务。

## 根据岗位要求替换的补充条目

根据岗位描述选择替换条目，每个项目保留 4–5 条即可。投递 RAG／大模型应用岗位时，优先增加知识检索和意图路由；投递全栈／平台岗位时，优先增加可视化工作流，并将相应技术补进技术栈。

- **FAQ 知识问答：** 构建 pg_trgm 高置信度直答、bge-m3 向量召回与 CrossEncoder 重排序的分级检索链路，将检索结果作为上下文驱动 LLM 回答，支持无来源兜底与检索过程追踪。
- **意图路由：** 实现关键词、历史及 Agent 描述向量、LLM Function Calling 三级级联路由，支持可配置处理目标、相似历史 few-shot 和低置信度澄清，将识别结果映射到下游 Agent。
- **可视化工作流：** 基于 Next.js 与 React Flow 实现流程编辑，将节点与连线配置动态编译为 LangGraph 执行图，支持 Agent 调用、条件分支和意图路由；通过 SSE 展示节点结果与耗时，打通编辑、保存、运行和调试流程。
- **提示词组装：** 按身份、角色、工具指导和运行上下文分段组装 System Prompt，由同一次工具求值生成 Schema 与使用指导；支持严格变量校验、配置逐轮生效和提示词预览，使工具定义与提示词同步更新。
- **异常场景验证：** 完成工具调度 32 项、会话恢复 12 项自检，全部通过；覆盖并发上限、乱序完成后的按序提交、独占屏障、取消结果补齐、中断轮次修复及消息合法性验证。

## 面试时约一分钟的介绍

这个项目是我独立开发的智能体运行平台（Agent Harness），应用场景包括智能客服、知识问答和工具执行。我主要解决的是模型开始调用工具以后，执行过程怎么受控、状态怎么保存，以及用户怎么在运行中纠正方向。

最直接的优化是多工具执行的等待：我实现了默认 4 路并发，同时通过独占屏障处理共享工作区操作，并按调用顺序提交结果。以 12 次各等待 100ms 的模拟 I/O 调用做对照，串行和并行各测 5 轮，中位耗时从 1.33 秒降到 0.35 秒，减少约 74%。这是调度层模拟基准。会话侧通过事件日志统一上下文和轨迹，并实现写入去重、中断修复与重启后续聊，12 项恢复测试全部通过。执行侧为受限调用提供 Docker 沙箱，升权通过人工审批，用户也能在运行中追加或修正指令。

我认为这个项目最有代表性的设计是工具调度与会话恢复：既要让任务执行有效率，也要保证异常、取消和重启以后，工具调用记录与模型上下文仍然可以被解释和继续使用。

## 面试追问与代码依据

| 追问 | 回答重点 | 代码依据 |
| --- | --- | --- |
| 为什么说这是 Harness？ | 平台实现了模型外部的执行循环、工具调度、状态记录、权限控制和运行中干预；可视化工作流是另一个配置入口。 | `backend/agents/runtime/agent_runtime.py`、`backend/agents/runtime/loop/agent_loop.py` |
| 为什么并发执行还要按序提交？ | 区分实际执行顺序与日志提交顺序；结果先进入缓冲，再按模型给出的调用顺序提交，使上下文和轨迹顺序稳定。不要把“所有模型协议都禁止乱序工具结果”说成通用结论。 | `backend/tool_system/runtime/scheduler.py` |
| 独占屏障用来解决什么？ | Bash / Python 等工具可能共享会话工作区；独占调用启动前排空在途任务，并在执行期间阻止新任务进入。 | `backend/tool_system/registry/descriptor.py`、`backend/tool_system/runtime/scheduler.py` |
| 重启后怎么恢复？ | 读取持久化事件并回放；若日志尾部存在未结束轮次，补记工具结果未知或未执行的事件，再闭合步骤和轮次。恢复不等于重新启动原来被中断的工具进程。 | `backend/agents/runtime/session/persistence/postgres.py`、`backend/agents/runtime/session/repair.py` |
| 用户中途发消息怎么办？ | 当前步骤修正进入 next-step 队列，追加任务进入 next-turn 队列；在步骤边界认领并追加 user/message 事件，使用 msg_id 将 SSE 回执与前端气泡对齐。 | `backend/agents/runtime/loop/inbox.py`、`backend/api/agents.py` |
| 提示词与工具定义怎么同步？ | 一次求值获得实际可见的工具 Schema 和 guidance，先确定工具集合，再组装工具指导段，避免分别维护两份工具说明。 | `backend/agents/runtime/system_prompt/assembler.py` |

## 当前实现边界与数据口径

- 这是个人项目。项目起止时间按实际开发时间填写，不把 Git 首次提交时间自动等同于项目开始时间。
- 本稿没有写用户量、成功率、P95 延迟或成本下降比例，当前查看的材料不足以证明这些指标。
- 会话恢复覆盖已经持久化的事件。主链路在轮次结束时批量写入，不能据此宣称执行中崩溃绝不丢状态。
- 双队列和运行登记表目前在进程内存中；待投递输入的持久化队列尚未实现，同会话互斥也不是分布式锁。
- 默认 4 路并发是调度配置，允许调整。本次 74.0% 的耗时下降仅适用于记录的模拟 I/O 基准；独占由工具声明决定，不是自动识别所有外部工具的副作用。
- 长期记忆模块存在，但 README 将“接入主 Agent Runtime”列为未完成项；不要写成主链路已实现长期记忆或自动上下文压缩。
- Docker 默认使用 bridge 网络；三种模式主要表达文件访问效果。只读与工作区可写模式经过 Docker，完全访问模式直接执行原始命令、不经过 Docker；升权申请不可用或未获批时保持原权限，不表示所有原权限内操作都被禁止。
- FAQ 检索先尝试 pg_trgm 高置信度直答，未命中再做向量召回和重排序；知识单元为 FAQ 问答条目，不描述为融合召回、文档分块或多格式文档摄取。
- 三级级联路由指通用 RouterRuntime；遗留 Supervisor 的实际 route() 只实现关键词和 LLM 两级，不将两套实现混写。可视化工作流没有持久化 checkpoint 或断点续跑。
- 仓库中的 `test_agent_loop.py`、`test_scheduler.py`、`test_repair.py`、`test_sandbox.py` 分别定义 44、32、12、85 个测试函数，共 173 个。数字表示静态统计的测试函数数，不表示全部测试已通过、测试覆盖率或业务成功率。
- 本次实际执行工具调度 32 项与会话恢复 12 项自检，全部通过；AgentLoop 和沙箱测试函数数仍仅为静态统计，没有本次运行通过的声明。

后续若要补充量化成果，优先测量：固定任务集成功率、相同工具集的串行/并行耗时、故障注入后的消息闭合与恢复情况。记录任务集、样本数、模型、配置和测量方式后，再将真实结果写进简历。
